Diagrama de Conexão do Banco de Dados

1 Arquitetura atual (localStorage)

O site é totalmente estático. Os dados do catálogo, eventos e acervo vêm de assets/js/data.js. Os dados do usuário ficam somente no próprio navegador, o que reduz a superfície de ataque e atende ao princípio da minimização (LGPD, art. 6.º, III). Nenhum dado é enviado a servidores.

2 Arquitetura futura (servidor SQL)

O navegador se comunicará por HTTPS com uma API. O servidor validará novamente todas as entradas, usará consultas parametrizadas (prevenção de injeção de SQL), armazenará apenas hashes de senha e tokens e aplicará as regras de retenção e eliminação da LGPD.

4 Plano de migração

  1. Provisionar o banco (SQLite em desenvolvimento, MySQL 8 em produção) e executar schema.sql e seed.sql.
  2. Implementar a API REST (por exemplo, GET /api/cardapio, POST /api/pedidos, POST /api/inscricoes, POST /api/admin/login) com HTTPS, limitação de taxa e CORS restrito.
  3. Substituir as leituras de data.js por chamadas fetch, mantendo os dados locais como reserva offline.
  4. Migrar a autenticação do administrador para o servidor (hash forte como Argon2/bcrypt, cookie HttpOnly; Secure; SameSite=Strict).
  5. Armazenar as imagens enviadas no servidor, reprocessadas e sem metadados EXIF.
  6. Registrar consentimentos em cookies_consentimento e implementar os endpoints de acesso e eliminação de dados (LGPD, art. 18).
  7. Atualizar a CSP (connect-src) para o domínio da API e testar ponta a ponta.
